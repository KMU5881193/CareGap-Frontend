# 백엔드 연동 인계

## 현재 경계

UI → AppController/ CareScope → CareRepository → MockCareRepository 구조입니다. CareRepository 인터페이스가 프론트에 필요한 작업 목록입니다. 실제 API URL·인증 방식·OpenAPI 문서가 제공되지 않아 엔드포인트를 임의로 만들거나 서비스에 접속하지 않았습니다. AppConfig.useMock=false는 실제 연결 준비 안내를 표시합니다. URL만 바꿔서 실서비스가 동작하지 않습니다.

## 기능별 책임

| 영역 | 프론트 구현 | 백엔드·운영에서 연결할 내용 |
|---|---|---|
| 계정 | 가입·로그인·복구·프로필·탈퇴 폼 | 인증/본인 확인, 세션 갱신·폐기, 오류 코드, 자격 심사 |
| 역할/연결 | 역할별 화면·연결 요청/허용/해제 | 서버에서 승인 상태·담당 관계·열람 범위 재검증 |
| 일정 | 가용 시간 선택·전이·중복 안내 | 시간대 UTC/ISO8601, 중복 잠금·버전 충돌·취소 정책 |
| 기록 | 편집·첨부·후속·인계 | 파일 업로드와 보관/삭제, 작성자 권한, 변경 버전, 공유 범위 |
| OCR/STT | 선택·녹음·동의·미리보기·수정 | signed upload URL 또는 multipart, 변환 작업 생성·상태 조회·화자/타임스탬프 |
| AI | 초안·근거·수정·검토·누적 선택 | 비동기 작업·원문 버전·근거 위치·누적 결과, 실패/재시도 |
| 복지 | 후보·검색·상세·즐겨찾기 | 출처 URL·갱신 시점·조건·공식 확인 절차 |
| 알림 | 목록·읽음·종류 설정·화면 이동 | 이벤트 저장·발송·읽음 동기화·장치 토큰·발송 설정 |
| 관리자 | 관리 화면·체험 상태 변화 | 관리자 인증·세분화 권한·감사 로그·검색·집계 API |
| 영상/전화/채팅 | 후속 UI 미리보기 | 도입 시점/사업자/세션 발급·시그널링·연결·동의·보관 정책 |

## API 합의 시 우선 확정

1. 역할·승인 상태 enum, 로그인 응답, me(), 갱신·만료·기기 로그아웃, 회원가입/심사 오류.
2. 목록 pagination/filter/sort, 오류 envelope(code,message,fieldErrors,requestId), idempotency와 리소스 version.
3. 상담 시간대와 요청·확정·변경·취소·완료/노쇼 권한. 현재 예시는 요청자가 자신의 요청을 승인하지 못하며 변경 수락 전 기존 시간을 유지합니다.
4. 가족 연결 승인/철회 시 즉시 데이터 회수. 현재 대상자와 가족은 승인·공개된 요약만 받고 원문/내부 메모/첨부는 받지 않습니다. 실제 범위는 정책 확정 후 서버에서 적용합니다.
5. AI 검토 승인과 대상자 공개를 별도 상태로 둡니다. 원문 수정 시 기존 AI 결과·승인을 무효화하고 서버도 동일 버전인지 재확인합니다.
6. 업로드 허용 형식·크기·보관·삭제·동의 식별자, 변환 jobId/status/원문 근거. 현재 파일은 실행 메모리에만 있습니다.
7. 복지 정보에 출처·확인 시각·조건을 포함합니다. UI 표시를 실제 지원 자격 확정으로 해석하지 않도록 합니다.
8. 운영 약관·동의 문구·탈퇴 데이터 처리·기록 인계 권한·응답 기간을 확정합니다. 현재 체험 탈퇴는 접근 중지이며 실제 데이터 삭제 정책이 아닙니다.

## 알림을 누가 구현하나요?

백엔드가 있다고 모바일 알림 작업이 없어지는 것은 아닙니다. 서버가 **언제 누구에게 보낼지** 결정하고, 앱은 **권한·수신·표시·탭했을 때 이동**을 맡습니다.

이 프로젝트에는 현재 알림 UI와 체험 설정만 구현되어 있습니다. 실제 발송은 Firebase 프로젝트, 앱 식별자, APNs 인증 키를 받은 후 firebase_messaging을 연결합니다. iOS 설정과 토큰 취득 전제는 [Firebase Flutter 설정 문서](https://firebase.google.com/docs/cloud-messaging/flutter/get-started)를 기준으로 맞춥니다.

권장 인계 방식:
- 앱: 맥락 있는 시점에 알림 권한 요청, device token 최초 등록·갱신 전송, 로그인/로그아웃 시 사용자와 기기 관계 갱신, 포그라운드/백그라운드/종료 상태 수신, 알림 탭 후 서버 권한을 다시 조회하고 리소스 화면으로 이동.
- 서버: 상담 확정·변경·일정 임박·검토 결과 등의 이벤트 생성, 수신 동의·종류 설정·가족 연결·담당 권한 확인, 중복 발송 방지, 실패 토큰 정리, 이력·재시도.
- 함께 합의할 API: 장치 토큰 등록/폐기, 알림 설정 저장/조회, 알림 목록/읽음, push payload의 eventId/type/resourceId. 이 이름들은 합의 항목이며 실제 엔드포인트로 구현하지 않았습니다.
- 메시지 전송용 자격 증명은 앱에 넣지 않고 신뢰할 수 있는 서버 환경에서 사용합니다. [FCM 서버 구성](https://firebase.google.com/docs/cloud-messaging/server-environment)
- 푸시 본문에는 상세 상담 원문을 싣지 않고 일반 안내와 리소스 ID를 사용하도록 설계합니다. 수신 상태별 처리는 [Flutter 메시지 수신 문서](https://firebase.google.com/docs/cloud-messaging/flutter/receive-messages)를 확인합니다.

알림 서버 일정 작업과 앱 로컬 예약을 둘 다 켜면 중복될 수 있으므로 일정 임박 알림의 발송 주체를 먼저 정합니다. 현재 프론트는 실제 발송 성공이나 OS 알림 허용을 가정하지 않습니다.

## 출시 전 남은 외부 연결

실제 API·푸시·OCR/STT·AI·실시간 상담, 공식 복지 출처, 운영 동의 문서, 앱 ID·배포 인증서·Apple 서명·스토어 정보와 기기 실측 QA가 필요합니다. 네이티브 빌드 성공과 체험 흐름 테스트는 앱스토어 심사·운영 검증을 대신하지 않습니다.
